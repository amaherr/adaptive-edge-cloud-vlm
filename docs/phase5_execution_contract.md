# Phase 5 adaptive execution contract

`adaptive-benchmark` runs the Phase 4 selector through the three resident Phase 1 policies. It requires a frozen manifest, Phase 3 calibration, and versioned replay JSON. The current local calibration has **failed G3** and the physical G4 gate is open. Its run is enabled only with the explicit `--diagnostic-allow-unpassed-gates` flag; a later campaign can omit that flag only when both `--predictor-evaluation` and `--selector-evaluation` report passing full gates for the same calibration ID. Phase 5 never silently promotes the local fit.

## Inputs and preflight

- `--config` and `--manifest` pin the model, generation settings, placement, request revision, image hashes, and seeded schedule. The command loads one full edge adapter, plus cloud and synchronous projected policies. Start a dual-path `adaptive-server` with the matching model fingerprint first. The runner checks remote capabilities before each decision and again if a safe retry is needed.
- `--calibration` must match the replay's calibration ID, source profile hash, model contract, and host pair. The replay pins the manifest SHA-256, task bucket, exact per-configuration placement profiles, a default network state, optional trial network overrides, and declared unhealthy candidates by request ID. The runtime edge/cloud device and remote address must match those placement profiles and their calibrated hashes. The replay file's SHA-256 goes into the plan and every raw row.
- The local full adapter counts the exact pinned query tokens **before** inference. The runner reads image byte length and decoded width/height before selection. No generated output length is fed into the predictor. A replay quality floor is rejected because Phase 5 has no validated predecision quality estimates. An edge memory budget requires a measured peak argument, and unknown candidate memory remains ineligible.
- The provided `configs/adaptive/phase5_local_replay.json` declares different candidates unhealthy across request IDs solely to exercise all three policies. Those flags are laboratory replay inputs, not observations of actual server faults. For a physical-host campaign, freeze a new replay and use real supported network/placement conditions; leave `unhealthy_by_request` empty unless testing a declared failure scenario.

## Decision and failure behavior

For each scheduled trial, `execute_adaptive_request` snapshots capabilities, predicts all three candidates, selects once, and dispatches that one policy. Health changes after selection do not reroute an in-flight inference. Every candidate prediction and exclusion reason is retained in the attempt's decision trace. A TCP connection failure **before any request bytes are sent** permits one fresh capability check and one new decision excluding the failed candidate. The record contains both attempts, each selection/execution time, and added retry time. Errors after connection or of unknown stage do not retry. Zero feasible candidates produce an explicit failed row without inference.

The run directory contains `plan.json`, `run_manifest.json`, `requests.jsonl`, and `summary.json`. `requests.jsonl` has exactly one terminal row per trial, including a warmup or failure, and can be resumed only with the identical plan and replay hash. Observed end-to-end time starts before feature extraction and ends after inference or failure; it includes all selection and retry overhead. Rows carry the selected configuration, all attempts, actual token/text/quality result, policy metrics, contract hashes, and latency. The summary reports choices, outcomes, retries, and latency/selection overhead. Existing fixed-policy `benchmark` and manual `adaptive-infer` commands are unchanged.

## Control analysis

`analyze-adaptive` compares the mixed run with **three** fixed-policy controls on the same manifest, model contract, semantic config, and exact warmup/repetition schedule. It does not use `compare-runs`, whose distinct fixed-mode contract cannot represent a mixed-choice run. For each successful adaptive row, it chooses the fixed reference corresponding to the selected mode, discloses placement mismatch, compares output token IDs on matching placements, and checks request/response wire-byte accounting for that mode. It also audits decision completeness, selected eligibility, bounded retry provenance, overhead accounting, row hashes, and exactly one terminal row per scheduled trial. `g5_local_gate_passed` requires a mixed choice, no failures, complete controls, matching same-placement tokens, valid wire accounting and traces. This is a correctness/integration gate, not a performance gate.

The local diagnostic's [handoff](phase5_handoff.md) gives runnable commands, artifacts, and the physical-host migration steps.
